> 判断依据全部来自读代码、跑检查、翻 git 历史以及本机真实运行数据（`monitor.log` / `state.json` / `messages.db`），**每条结论都尽量附上证据**；凡是推测都会标明「推测」。
> 与其它文档的分工：[`onboarding-notes.md`](onboarding-notes.md) 讲「现在是什么样」，[`web-design.md`](web-design.md) / [`v2-design.md`](v2-design.md) 讲「已经做了什么、原来打算做什么」，**本文讲「还差什么、下一步该做什么、哪些明确不该做」**。

## 一、先说结论

这个项目**工程质量在同类自用工具里属于上游**：约束清晰（全本地 / 零构建 / 纯标准库）、跨文件契约有明确记载、关键坑位都有 commit 级别的注释解释「为什么这么写」、离线验证手段（`--mock`）完备。

但它的**真正短板不在代码，而在"闭环"**：

| # | 一句话结论 | 证据 |
|---|---|---|
| 1 | **它是一个"哑"监控器**：抓取失败时自己知道、也写进了日志和状态栏，但用户不在屏幕前时收不到任何信号。真实数据里它已经**连续静默失败数月**。 | `monitor.log` 3,711 行中 **3,693 行是抓取失败**（`Errno 2` 2,230 行、`timed out` 104 行），而**自 2026-06-03 起再无一条成功推送记录**；日志跨度 2026-06-03 → 2026-09-14 |
| 2 | **"Windows 桌面小工具"这个定位没有兑现**：它实际是「一个浏览器标签页」，关掉标签页/浏览器就失去感知，开机不自启，没有托盘图标。 | `README` 明确写"关掉浏览器标签页程序不会退出"，但用户在副屏盯盘时**没有任何界面外的存在感**；`v2-design.md` 的"系统托盘 + 开机自启"至今未做 |
| 3 | **降噪只做到了"按人静音"这一层**，而盯盘的真实噪音源是**话题/标的**，不是人。 | 侧栏筛选只有"按用户 / 按类型"（`web/app.js` 的 `filter{user, kindOff}`）；7 个活跃监控用户一天能产生数百条（`state.json` 里多个来源的 500 条去重窗口已被打满），却无法按"是否提到我的持仓"过滤 |
| 4 | **沉淀了 4,605 条数据却几乎没有利用**：搜索是 `LIKE '%kw%'` 无排序、无时间范围、无聚合、无导出。 | `monitor.search_messages()` 仅三个字段 LIKE + 按时间倒序取 100；`messages.db` 已有 4605 行 / 1.6 MB，时间跨度 2026-07-02 → 2026-09-14 |
| 5 | **配置与去重状态之间没有生命周期管理**，删过的监控对象会留下"僵尸基线"。 | `state.json` 里 23 个来源中有 **11 个已不在 `config.json` 中**（含 4 个 `tw:` 推特来源、3 个 `ap:*` 追加残留）：这些 key 永远不会被清理也不会被更新 |
| 6 | **两个入口共享 `state.json`，同时运行会互相"吃掉"对方的推送**。 | `monitor.py` 的 `check_user()` 用 `uid not in state` 判首轮，`core.py` 的 `_emit()` 用 `_seeded`；两者读写**同一个** `state.json`，谁先跑谁的基线生效 |
| 7 | **已开源，但文档跑在实现前面**：README 里的"毫秒级响应""三态主题切换""轮询退避策略"与代码实测不符。 | `toggleTheme` 只在两态切换（"跟随系统"无 UI 入口）、退避只存在于"查追加"、真实延迟是 30~60 秒轮询级 —— 逐条对照见 §3.5 |

如果只能做一件事，**做第 1 条**（抓取健康度 + 自愈）：其余所有功能都建立在"数据是真的在进来"这个前提上，而这个前提在本机已经被打破了至少三个月而无人察觉。

## 二、使用这个项目的人，到底要什么

先把需求想清楚，否则路线图会变成功能清单的堆砌。从 README（含最新的开源门面版）、`v2-design.md` 的功能取舍和 UI 细节里可以还原出这个用户画像（**这些不是猜的，都能从代码与文档里读出来**）：

- 用**竖屏副屏**盯盘（README 明说"放在竖屏副屏上正合适"；`web/app.css` 的断点 1150/900/560px、侧栏窄轨、紧凑模式都是为这个形态做的）。
- 关注的是**A 股情绪面/游资动向**，不是长文阅读：所以有"评论/转发"这类短内容混排、股吧吧名展示、一键跳行情（`POPULAR_STOCKS` + 8 种股票代码写法识别）。
- **开盘时段高度在场**，但**离开工位时需要被通知到**：所以有声音提示、"上次看到这里"断点线、标签页未读数、以及原始的微信推送诉求。
- **不能接受"被打扰"**：所以有按用户静音、通知合并阈值 `MERGE_LIMIT`、轮询间隔可调、推特微博故意放慢。
- **在意隐私与确定性**：本地运行、无云依赖、无额度上限、`config.json` 不入库。
- **在意"我已经配好了，请让它一直跑"**：所以有自动开始监控、历史持久化、启动即加载。

提炼成需求层级：

| 层级 | 需求 | 现状 |
|---|---|---|
| **基础（必须永远成立）** | 抓取可靠、失败可知、数据不丢 | ⚠ **已被打破**（见 §3.1） |
| **核心** | 有动静就告诉我（屏幕内 + 屏幕外） | 屏幕内 ✅ ／ 屏幕外 ❌（微信推送是独立命令行版，且额度受限） |
| **核心** | 别用噪音淹没我 | 半成品（只能按人静音） |
| **进阶** | 我要回头查"谁在什么时候说过什么" | 雏形（弱搜索、无聚合、无导出） |
| **进阶** | 它应该像个常驻桌面程序 | ❌ 只是个网页 |

## 三、不足清单（按严重度分级，附证据与影响）

### 3.1 P0 — 会让整个工具"静默失效"的问题

#### (1) 没有抓取健康度与自愈机制 ★最严重

**现状**：单个来源抓取失败只有两条出路——`set_status()` 刷一行状态栏文字、`monitor.log` 追一行日志。状态栏文字会被下一次成功覆盖，日志没人看。

**证据**：
- `monitor.log` 共 3,711 行，其中含「失败」的 **3,693 行（99.5%）**；`Errno 2` 出现 **2,230 次**、`timed out` **104 次**。
- 最后一次"发现新动态/已推送"类成功记录停在 **2026-06-03 16:00**；日志末尾停在 **2026-09-14 17:00**——**中间 3 个半月只有失败**。
- 日志里 `限流` / `cookie` / `ok=` 相关记录为 **0**：说明失败**不是**被反爬拦截，而是网络层直接不可达（`Errno 2` 在 `urllib` 下通常意味着代理解析/连接建立失败）。**推测**：该机器长期处于某种代理环境，而 `monitor.fetch_json()` / `parse_post_appends()` 直接用 `urllib.request.urlopen`，**不读系统代理、也没有显式代理配置**。

**为什么这是 P0**：用户在 README 里被承诺"关电脑就停，但电脑开着就在监控"。**实际上"没在监控"和"在监控但没新动态"在界面上长得一模一样**——状态胶囊只显示 `运行中` + 上次检查时间，而"上次检查"哪怕全部来源都失败了也会被刷新（`_run_loop` 末尾无条件 `self.last_check = ...`）。这是**最危险的欺骗性状态**。

**影响面**：所有依赖数据的下游功能（通知、列表、搜索、追加检查）在静默失效期间全部无意义，而用户会以为自己在被保护。

#### (2) 抓取层没有代理 / 重试 / 退避（只有追加检查有）

- `monitor.fetch_json()`：裸 `urllib.request.urlopen`，**无重试、无退避、无代理**。
- 全项目**唯一**有失败退避的是"查追加"（`core._append_backoff_interval`）。股吧主列表、评论、推特、微博**都没有**——失败就下一轮再来，30~60 秒一次，一直撞墙。
- 这正是 §3.1(1) 里 3 个半月失败的成因之一：失败了不降频，还按原节奏一直打，同时**不给用户任何升级信号**。
- `monitor.py` 的 `log()` 每次追加文件、永不轮转（当前 0.39 MB / 3,711 行）；`state.json` 每轮结束**无条件重写**（`save_state`），哪怕内容没变。

#### (3) 两个入口共享 `state.json`，同时运行会互相破坏推送

`python monitor.py`（命令行微信版）与 `python server.py`（网页版）读写**同一个** `state.json`：
- 网页版先跑 ⟶ 命令行版这一轮看到的 key 全在 `state` 里 → 什么都不推。
- 命令行版先跑 ⟶ 网页版 `_emit` 的 `state[skey]` 已含这些 key → `new_items` 为空 → **不弹通知、也不入列表**（因为不是首轮基线，`_emit` 直接走 `elif new_items` 分支，空则什么都不做）。
- 二者还会互相覆盖对方的 500 条窗口（`state[skey] = ...[:500]`）。

**风险**：这不是"可能发生"，而是**只要用户同时开着两个入口就必然发生**，且表现是"推送莫名其妙少了"，极难排查。README 里只说"命令行版有额度限制"，没提这个冲突。

#### (4) 抓取失败的**部分成功**对用户不可见

`monitor.collect_items()` 把 `parse_posts` 和 `parse_replies` 分别 `try/except`，**只 `log()` 不抛异常**。于是：
- 发帖抓到了、评论全失败 → `collect_items` 返回非空 → `core` 认为"该来源本轮成功" → 正常 `_emit`、正常刷新"上次检查"。
- 用户完全不知道评论这条路已经断了，还可能因为"评论抓不到 → 没新 key"而在**恢复后**引发一次小规模的历史刷入。

#### (5) 抓取完全串行，活跃用户会拖垮整轮

`_run_loop` 里每个用户、每个来源都是 `for` 循环 + `stop_event.wait(random.uniform(2, 4))`。7 个股吧用户 ≈ 每题至少 2 次 HTTP + 2~4 秒等待，一轮轻松超过 30 秒；再叠加 300 秒节奏的追加检查（每条帖子一次详情页请求），**用户越多，"实时性"越差**，而 README 承诺的延迟是"约等于轮询间隔"。没有任何优先级、并发或"只抓最近活跃用户"的调度。

### 3.2 P1 — 明显缺失的核心能力

#### (6) 没有"关键词 / 标的订阅"——降噪只做到按人

盯盘的真实噪音模型是**"我关心的话题"**，不是"我关心的人"。现在的能力粒度只有「按用户静音」+「按类型筛选」。

缺的：
- 关键词/股票代码订阅 → 命中时**高亮 + 提升通知优先级**（甚至可配 Windows 通知的声音/横幅）；
- 关键词订阅 → **独立于用户列表的第二条捕获通道**（即使没监控那个人，提到我的持仓也要提醒）；
- 优先级分级：置顶/高亮 `关注标的`、折叠/低优先级处理"纯情绪发言"。

`v2-design.md` 里完全没提这一项——这是**需求侧最大的盲点**。

#### (7) 搜索是"能用"级别，离"盘活数据"很远

`monitor.search_messages()`：
```sql
WHERE content LIKE ? OR bar LIKE ? OR name LIKE ? ORDER BY time DESC, key DESC LIMIT ?
```
问题：① 无相关性排序（只能按时间）；② 无时间范围过滤（"上周谁提过 XX"做不到）；③ 不搜 `kind`/股票代码（股票代码只在 `content` 里，靠 `/api/search` 的 `content` 命中尚可，但 `bar` 之外无处可查）；④ 前端把搜索结果当**一张平铺列表**渲染（`searchDb` 直接替换 `filteredShown`），**丢失了日期分组、折叠、按用户筛选**，200 条结果里找东西全靠滚；⑤ 没有"跨用户看同一标的"的聚合视图——而这恰恰是盯盘最想要的。

#### (8) "上次看到这里"是易失的

`lastSeenKeyRef` / `firstUnreadKey` 只存在 React 内存里（`useState`），**刷新页面即丢**。用户在副屏盯盘，F5 一下或者浏览器崩溃恢复，断点线就没了。`v2-design.md` §8.4 里规划的"上次看到这里分割线（记录最后浏览的 key）"其实只做了一半——**没有持久化**。

#### (9) 手机/离开电脑时的通知链是断的

- 网页版**完全没有**手机推送：`core._handle_new()` 只调 `toast()`（Windows 通知）。
- 微信推送只在**独立的命令行版**里（`monitor.py` 的 `main()`），且**只处理股吧用户**、Server酱免费版每天 5 条。
- 结果：用户白天在电脑前用网页版（体验好但离不开电脑），想手机收提醒就得**再开一个命令行版**——而这正好触发 §3.1(3) 的 `state.json` 冲突。

这是一个**结构性断裂**，不是缺功能：同一个需求（"离开电脑也要被通知到"）被两个互斥的入口瓜分了。

#### (10) 追加检查的窗口硬编码 24 小时

`_register_append_watch()` 与 `_check_append_watch()` 里 `86400` 出现两次。而股吧的"追加"行为在现实中经常发生在**发布后数天**（尤其连载式的复盘帖）。用户无法调整这个窗口，也无法对单个帖子"手动续期"。

### 3.3 P2 — 体验与产品化欠缺

#### (11) 不是一个"桌面程序"

没有系统托盘、没有开机自启、没有"最小化到托盘"。关掉浏览器标签页 = 失去一切可见性（进程还在跑，但用户看不到状态、也不知道有没有新动态）。对"电脑常开、盯盘一整天"的场景，这是**定位级缺失**。

#### (12) 界面是单文件 1,058 行的 `app.js`

零构建约束下的合理取舍，但已经出现明显症状：`App()` 一个组件里塞了 ~20 个 `useState`、SSE 装配、搜索、滚动、未读、声音、筛选、分组、股票字典…… 继续加功能（关键词订阅、聚合视图）会让它难以维护。**不需要上构建**，但需要"**自写的极简模块拆分**"或至少把纯逻辑（股票识别、正则、格式化）抽到独立文件（`web/index.html` 加一个 `<script>` 即可，无需任何工具链）。

#### (13) 僵尸基线与状态膨胀

`state.json` 23 个来源、**11 个已不在 `config.json`**。它们在 `list_users()` 里不出现（因为 `list_users` 只遍历启用的来源），所以用户**根本没有办法看到或清理它们**。当前无害（只是文件大 + 重写开销），但：**用户删掉某人再加回来，行为不可预测**（可能"新内容"被当成基线吞掉，而不是弹通知）。缺少"删除监控用户时同步清理其 `state.json` 条目"的逻辑。

#### (14) 日志与磁盘无节制

- `monitor.log` 永不轮转（`log()` 纯追加）。
- `messages.db` 永不清理/归档（`v2-design.md` 也没提）。
- `state.json` 每轮无条件重写。
- 相对小，但属于"跑一年会出问题"的类别。

#### (15) `/api/users` 与 `core.save_users()` 已成为死代码

前端设置抽屉已全面改走 `/api/users/manage`（`manage_config`），`save_users` 与 `mock_data.MockCore.save_users` 没有调用方了，但仍占着 40 行 + 一条路由 + 一份 `onboarding-notes` 里的解释成本。

#### (16) 遗留 tkinter 版与依赖

`app.py`（649 行）+ `run_gui_tk.bat` + `sv_ttk` 依赖一直挂着。`web-design.md` 阶段 7 的条件（"稳定运行 ≥ 1 周"）从 2026-09-14 起**早已满足**（已合并进 main），但清理一直没做。副作用：每次改配色/用户列表逻辑都要在**两个文件**里同步（`KIND_BG`、`_resolve_fg`、`open_colors` 的 `rows`/`editable_users`、`ENABLE_*` 开关），这是持续的税。

### 3.4 P3 — 工程卫生

#### (17) 没有任何自动化测试

零测试覆盖下，风险最高的是这几处**纯函数/纯语义**（完全可测，且历史上真出过错）：
- `_norm_time()` / `_parse_weibo_time()`（时间格式错 → 分组排序错乱，静默）；
- `_extract_js_object()`（手写大括号配平状态机，含字符串/转义处理）；
- `parse_news_link()`（正则反解）；
- `_emit()` 的首轮基线/去重语义（历史上出过 commit `7a3d470` 那种"某来源永不显示"的 bug）；
- `load_messages_before()` 的二元游标（同一秒多条不重不漏）；
- `_append_backoff_interval()` 的退避曲线（含封顶）。

**这些都不需要网络、不需要 UI、不需要框架**——`unittest` + 假数据就够，成本极低，收益是"改抓取/解析时敢动手"。

#### (18) 少量其它小问题

- `mock_data.MockCore` 覆写 `refresh_config_maps` 等一堆方法，**与父类的接口一致性只靠人脑维持**（父类加一个方法，mock 可能悄悄用错实现）。
- `/api/search` 无输入长度限制与速率限制（本地端口，风险低但不优雅）。
- 前端 `CTX_RE` 与后端 `_add_item()` 的前缀拼接格式是**隐式契约**（改一处忘另一处 = 上下文静默丢失），只在注释里写了，没有测试。
- `ENABLE_TWITTER` / `ENABLE_WEIBO` 是**代码级常量**，恢复来源要改代码 + 重启，而不是配置项。

### 3.5 文档 / 实现偏差（开源门面下的新问题）

项目已公开发布，README 从"使用说明"变成了"产品门面"，于是下面这些**实测出来的不一致**从"无伤大雅"升级成了"会被 issue 打脸/被误解为已实现"：

| # | README 的说法 | 代码实测 | 性质 |
|---|---|---|---|

## 四、问题归因：哪些是设计约束的代价，哪些是真正的欠账

这一点很重要——**不是所有不足都值得修**。

| 类别 | 项目 | 判断 |
|---|---|---|
| **约束的合理代价（不要修）** | 无云依赖导致手机推送要靠 Server酱这类第三方；浏览器承载 UI 导致"关标签页仍在跑"的认知落差；零构建导致单文件前端 | 这些是**刻意的取舍**，README/设计文档都写明了理由。修它们等于换项目 |
| **接口风险的必然（只能缓解）** | 非官方接口随时变、详情页易触发反爬、推特 Cookie 易失效 | 无法根治，但**可以做到"失败时让你知道 + 自动降频"**（§3.1(1)(2)），这才是欠账 |
| **真正的欠账（该修）** | 抓取健康度/自愈、`state.json` 冲突与僵尸条目、关键词订阅、搜索与聚合、未读断点持久化、托盘/自启、追加窗口可配、测试、旧版清理 | 全部是**在既有约束内可以做好**的事 |

**一句话**：这个项目的架构选择是对的，问题几乎全部出在"**运行时状态的可观测性与生命周期管理**"这一层——也就是"它跑起来之后，你没看着它的那段时间里发生了什么"。

## 五、后续开发方向（路线图）

排序原则：**先保证数据是真的 → 再保证你能被叫醒 → 再降噪 → 再用数据 → 最后产品化与还债**。

### P0：让"静默失效"不可能发生（≈ 2~3 次会话）

| 项 | 具体做法 | 涉及文件 |
|---|---|---|
| **抓取健康度面板** | ① 给每个来源维护 `last_ok_at` / `last_error` / `连续失败次数`，进 `/api/snapshot` 的 `status`；② 状态胶囊区分「运行中 / 部分失败(N) / 全部失败」三态，失败时变`--warn`/`--danger`色并在侧栏列出是哪个来源、什么错；③ 顶部横幅：连续失败 ≥ N 次时常驻提示，且**提供"一键诊断"** | `core.py`（新增 `self.health`）、`server.py`、`web/app.js` |
| **失败自动退避 + 重试** | 把"查追加"那套退避**抽成通用工具**（`_backoff_interval(streak, base, cap)`），股吧/评论/微博/推特全部套用；单次请求加 1~2 次带抖动的重试；失败连续超过阈值时**主动发一条通知**（"抓取已连续失败 30 分钟，最后一次成功 xx:xx"）——这是"屏幕外也能知道"的最低成本实现 | `core.py`、`monitor.py`（`fetch_json` 加可选代理参数） |
| **代理支持** | `fetch_json` / `parse_post_appends` / `parse_weibo` / 推特子进程统一走一个 `_opener()`，读 `config.json` 的 `proxy` 字段（并可选读环境变量 `HTTPS_PROXY`）。**这条能直接解决本机 3 个半月的失败**（推测成因） | `monitor.py` |
| **"上次检查"不再撒谎** | `last_check` 拆成 `last_cycle_at`（循环跑完）与 `last_success_at`（真正抓到数据），前端主显后者 | `core.py`、`web/app.js` |
| **`state.json` 生命周期** | ① 删除监控用户时同步移除其 skey（`manage_config` 的 `delete` 分支）；② 每轮或每 N 轮清理"不在 config 中"的僵尸 skey；③ 加 `state.json.bak` 或写前 rename（现在是裸覆盖）；④ **双入口冲突**：给 `state.json` 加 `owner` 标识 + 文件锁，检测到另一入口在跑时**明确报错并拒绝启动**（比静默互相吞推送好得多） | `core.py`、`monitor.py` |
| **文档校准（零成本，立刻做）** | 按 §3.5 表逐条修正 README：① 删掉"毫秒级响应"或改准确；② 补上"跟随系统"主题的真实 UI 入口（或把文档改成两态）；③ 架构图去掉"退避策略"或把退避真正做到主轮询；④ 快捷键表改成"按钮与操作"；⑤ `/api/items` 默认值改 200；⑥ `/api/users` 标注废弃或直接删；⑦ 结构图补新文档 | `README.md`、`web/app.js`（仅第 ② 项涉及代码） |

**验收标准**（沿用本项目"完成标准"的写法）：
- [ ] 手动把 `config.json` 的某个 uid 改成不存在的号 → 30 秒内界面出现「部分失败」且指名道姓
- [ ] 断网 5 分钟 → 收到一条"抓取失败"的通知；恢复网络 → 状态自动回到正常、通知一条"已恢复"
- [ ] 删掉一个监控用户 → 其 skey 从 `state.json` 消失
- [ ] 同时启动 `monitor.py` 与 `server.py` → 后者明确报错提示，而不是静默少推送
- [ ] README 里的每一条功能描述都能在代码里指到实现（对照 §3.5 表逐条勾掉）

## 六、明确不建议做的（防止后续走偏）

1. **不要引入前端构建链**（Vite/webpack/TS 编译）。项目的"零构建、离线可用"是产品特性，不是懒惰。拆文件用多个 `<script>` 或 IIFE 就够了。
2. **不要引入 Flask/FastAPI/ORM**。`http.server` + `sqlite3` 已验证够用；换框架会把"双击 bat 就能跑"变成"先建虚拟环境"。
3. **不要做账号体系 / 云端同步 / 多设备服务端**。这会把"本地隐私工具"变成需要运维的服务，与 README 的承诺冲突。
4. **不要为了"看起来更实时"把轮询间隔调到 10 秒以下**。现在已经处在被限流/封号的边缘（`CLAUDE.md` 明确警告），提高实时性的正确方向是**智能调度**（活跃用户优先、失败降频、追加检查与主轮询解耦）而不是整体提速。
5. **不要重写抓取层去用第三方库（如 `requests`/`httpx`）**。加依赖要慎重；`urllib` 的问题（无代理、无重试）可以用 20 行封装解决，不需要换库。
6. **不要在 `app.py` 里加任何新功能**。它的唯一结局是被删除（P3）。

## 七、如果只想做三件事（外加一件今天就该做的）

**另外，今天就顺手做掉**：按 §3.5 表校准 README + 补上"跟随系统"主题入口 + 删掉/标注死接口 —— 半小时的量，但它决定"项目说的话能不能当真"。**已开源的项目，文档失真比代码 bug 更伤**。

1. **抓取健康度 + 失败通知 + 代理支持**（P0）——让"在监控"重新变成一句真话。**没有这一条，后面所有功能都是在给一个不工作的管道做装修。**
2. **关键词/标的订阅 + 聚合视图**（P1）——把"盯着 7 个人"升级成"盯着我关心的标的"，这是盯盘场景的真实需求，也是 `messages.db` 里 4,605 条数据的正确用法。
3. **托盘 + 开机自启 + 推送统一**（P2）——把它从一个"需要记得打开的网页"变成"开机就在、离开也能叫醒你"的桌面工具。

做完这三件，这个项目会从"一个写得挺干净的自用脚本"变成"**一件可靠的盯盘工具**"。而这三件**都不需要牺牲它现有的任何一条设计约束**。
